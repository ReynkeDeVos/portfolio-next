# Section navigation, router history and hydration

Checked 2026-10-03 against the code at `7a1bb0d`, before the refactor; repository links point there. Section navigation (`src/components/section-navigation.tsx`) follows from these findings.

Router findings apply to installed `@tanstack/react-router` 1.170.41 and `@tanstack/react-start` 1.168.60, with **router-core 1.171.34 and history 1.162.4**. These transitive versions matter: react-router’s version alone does not identify the history implementation. Radix findings apply to `radix-ui` 1.6.7, which uses Tabs 1.1.21 and Roving Focus 1.1.19, with React 19.3. (Router dependencies: `@tanstack/react-router package.json:80`, Start version: `@tanstack/react-start package.json:3`, Radix dependencies: `radix-ui package.json:72`.)

## 1. Does direct `replaceState` notify TanStack Router?

**Yes, after this browser-history instance is installed. The current Section update bypasses the router navigation API, but does not bypass router observation.** History 1.162.4 wraps both native `pushState` and `replaceState`. Each wrapper calls the original method, reparses the browser location and notifies subscribers unless an internal suppression flag is set. It also listens to `popstate`; it does not rely on that event alone. Destroying the instance restores the original methods. (History wrappers and listeners: `@tanstack/history@1.162.4 src/index.ts:586`, Reparse and notify: `@tanstack/history@1.162.4 src/index.ts:428`, Cleanup: `@tanstack/history@1.162.4 src/index.ts:551`.)

React Router’s mounted `Transitioner` subscribes `router.load` to history. Loading updates `latestLocation` and publishes the location into router state. Thus `router.state.location`, `useLocation` and `useRouterState` notice through the load/store pipeline; a direct call is not a guarantee that every React observer has rerendered before it returns. (History subscription: `@tanstack/react-router src/Transitioner.tsx:39`, Router load: `@tanstack/router-core@1.171.34 src/router.ts:2423`, Location publication: `@tanstack/router-core@1.171.34 src/load-client.ts:2037`.)

`<Link>` subscribes to the location store and builds its destination from that location plus its options. Active state includes path and, by default, search; hash comparison is opt-in through `activeOptions.includeHash`. The Locale links specify only `exact: true`, so their active state does not distinguish Sections. Their destination hash comes explicitly from React Section state. (Link building and subscription: `@tanstack/react-router src/link.tsx:304`, Active comparison: `@tanstack/react-router src/link.tsx:90`, [Locale link](https://github.com/ReynkeDeVos/portfolio-next/blob/7a1bb0d/src/components/site-controls.tsx#L32).)

History stores `__TSR_index`, `__TSR_key` and legacy `key`. Its own push increments the index; replacement retains the index; both assign a new random key. A direct native replacement does **not** perform that assignment. This repository passes `history.state` back unchanged, preserving the index, keys and other existing state. Passing `{}` or unrelated state could remove metadata: traversal direction and blocker rollback use index differences, while scroll restoration uses `__TSR_key` with an href fallback. (Index assignment: `@tanstack/history@1.162.4 src/index.ts:206`, Key assignment: `@tanstack/history@1.162.4 src/index.ts:283`, Traversal: `@tanstack/history@1.162.4 src/index.ts:444`, Scroll key: `@tanstack/router-core@1.171.34 src/scroll-restoration.ts:46`, [Current replacement](https://github.com/ReynkeDeVos/portfolio-next/blob/7a1bb0d/src/components/portfolio-page.tsx#L54).)

Consequently, repeated Section replacements leave one history entry containing the latest Section; Back does not undo each Section choice. A later Locale navigation normally pushes another entry with a new key and incremented index. Back returns to the previous Locale entry’s last replaced hash, and Forward returns to the newer entry. This follows from replacement semantics, preserved metadata and the Locale link’s explicit hash; it is a source-derived conclusion, not a browser test. ([WHATWG URL/history updates](https://html.spec.whatwg.org/multipage/browsing-the-web.html#url-and-history-update-steps), Link navigation: `@tanstack/react-router src/link.tsx:450`.)

Native `replaceState` fires neither a traversal `popstate` nor `hashchange`; router notification comes from the wrapper. The WHATWG algorithm explicitly excludes `hashchange`. The page’s own `setSection` therefore handles its clicks, while its `hashchange` listener handles fragment changes from other navigation. Direct replacement also bypasses the history API’s blocker checks and router navigation options. ([WHATWG algorithm](https://html.spec.whatwg.org/multipage/browsing-the-web.html#url-and-history-update-steps), History blocker checks: `@tanstack/history@1.162.4 src/index.ts:159`, [Section synchronization](https://github.com/ReynkeDeVos/portfolio-next/blob/7a1bb0d/src/components/portfolio-page.tsx#L30).)

## 2. Supported hash navigation and hydration behavior

**Use `router.navigate` with `hash`, `replace: true`, `resetScroll: false` and `hashScrollIntoView: false`; `useNavigate` and `<Link>` delegate to the same navigation API.** Omitted `to` resolves to the current route. To change _only_ the hash while preserving a query such as `?ref=...`, also preserve search with `search: true`; omitted search otherwise becomes empty here. Preserve application history state explicitly if needed. Hash strings have no leading `#`; an empty string clears the hash. (Destination resolution: `@tanstack/router-core@1.171.34 src/router.ts:1959`, Search, hash and state construction: `@tanstack/router-core@1.171.34 src/router.ts:2103`, useNavigate: `@tanstack/react-router src/useNavigate.tsx:34`.)

Replacement and scroll flags are implemented in router-core and corroborated by the current official [NavigateOptions documentation](https://tanstack.com/router/latest/docs/api/router/NavigateOptionsType). The docs are unpinned; the installed source is the version-specific evidence. A router commit assigns hash-scroll state and the reset-scroll flag. The current manual replacement supplies neither option, so it can retain an earlier hash-scroll setting and use the current/default reset behavior. (Commit options: `@tanstack/router-core@1.171.34 src/router.ts:2305`.)

**Hash navigation still enters route loading and publication; it is not a location-only shortcut.** The router rematches routes, updates location state and publishes matches. `head()` and route scripts are evaluated during the normal client projection stage. This repository’s root and Locale routes have `head()` functions and no loaders. (Client load: `@tanstack/router-core@1.171.34 src/load-client.ts:1919`, Head evaluation: `@tanstack/router-core@1.171.34 src/load-client.ts:1252`, Projection invocation: `@tanstack/router-core@1.171.34 src/load-client.ts:1434`, [Root route](https://github.com/ReynkeDeVos/portfolio-next/blob/7a1bb0d/src/routes/__root.tsx#L20), [English route](https://github.com/ReynkeDeVos/portfolio-next/blob/7a1bb0d/src/routes/index.tsx#L6), [German route](https://github.com/ReynkeDeVos/portfolio-next/blob/7a1bb0d/src/routes/de.tsx#L6).)

Loader execution is conditional. In core 1.171.34, an unchanged successful match does not reload merely because its default stale time is zero: the decision also checks invalidation, `shouldReload`, same-href reload, entry or changed match identity. A changed hash changes href, so the ordinary unchanged-match case does not force a loader rerun. Location subscribers rerender when their selected value changes, but matched page components need not remount or all rerender: `MatchInner` memoizes the route element and uses configured remount dependencies. (Loader decision: `@tanstack/router-core@1.171.34 src/load-client.ts:765`, Same-href decision: `@tanstack/router-core@1.171.34 src/load-client.ts:1962`, Route element reuse: `@tanstack/react-router src/Match.tsx:194`.)

The render commit passes through view-transition handling. Browser view transitions require a navigation option or router default plus browser support; this repository sets no default. Scroll restoration still receives `onRendered`, but both false scroll flags suppress its restoration/top-scroll and hash `scrollIntoView` actions for that navigation. They do not prevent layout changes from affecting the viewport. (View-transition handling: `@tanstack/router-core@1.171.34 src/router.ts:2436`, Render commit: `@tanstack/router-core@1.171.34 src/load-client.ts:1860`, Scroll handling: `@tanstack/router-core@1.171.34 src/scroll-restoration.ts:250`, Scroll guards: `@tanstack/router-core@1.171.34 src/scroll-restoration.ts:310`, [Router configuration](https://github.com/ReynkeDeVos/portfolio-next/blob/7a1bb0d/src/router.tsx#L6).)

**`useLocation({ select: l => l.hash })` and the equivalent `useRouterState` selector are reactive, but do not guarantee hydration parity for hash-dependent markup.** Server rendering reads the server location store; client rendering subscribes to the client store. Client router hydration explicitly publishes the browser location, including its hash. React Store supplies the same current-store getter for both client and server snapshots, rather than retaining an empty server hash snapshot. Rendering a non-Work Tabs value immediately from that hash can therefore disagree with prerendered Work markup. (useLocation: `@tanstack/react-router src/useLocation.tsx:53`, useRouterState: `@tanstack/react-router src/useRouterState.tsx:57`, Browser hydration location: `@tanstack/router-core@1.171.34 src/load-client.ts:2232`, Snapshot getters: `@tanstack/react-store@0.11.2 src/useSelector.ts:58`.)

Router location hashes also omit `#`, whereas the repository’s `sectionFromHash` always removes the first character. That helper cannot consume `location.hash` from the router unchanged. (Router hash parsing: `@tanstack/router-core@1.171.34 src/router.ts:1481`, [Section parsing](https://github.com/ReynkeDeVos/portfolio-next/blob/7a1bb0d/src/lib/section.ts#L17).)

## 3. Radix Tabs before hydration

**The CSS-selected Section and Radix’s semantic selection disagree until React reconciles them.** Work retains `aria-selected="true"` and `data-state="active"`; the visually selected alternate trigger remains false/inactive, and panel `data-state` likewise follows Work. The script changes only the root dataset, and CSS changes styling and display. IDs, roles, `aria-controls` and `aria-labelledby` still connect the correct trigger/panel pairs. (Tabs selection attributes: `@radix-ui/react-tabs@1.1.21 dist/index.mjs:102`, [Root mark](https://github.com/ReynkeDeVos/portfolio-next/blob/7a1bb0d/src/lib/section.ts#L37), [CSS override](https://github.com/ReynkeDeVos/portfolio-next/blob/7a1bb0d/src/styles.css#L277).)

There is **no stale `hidden` attribute in this implementation**: `forceMount` makes every panel present, and Radix sets `hidden` to the inverse of presence. CSS controls which panel displays, including the wrapper’s inactive-panel rule. The visible alternate panel remains labelled by its own trigger, but that trigger is still announced as unselected. (Panel presence and attributes: `@radix-ui/react-tabs@1.1.21 dist/index.mjs:153`, [Wrapper visibility rule](https://github.com/ReynkeDeVos/portfolio-next/blob/7a1bb0d/src/components/ui/tabs.tsx#L55).)

The prerendered roving-focus state also differs from an operational tab widget: **the tablist and every trigger start at `tabindex="-1"`**, including Work. The current tab-stop ID starts null and registered focusable-item count starts zero; registration and keyboard handling require client effects. Panel tabindex is explicitly supplied by this repository according to panel content, so it is not a selected-trigger tabindex that CSS must transfer. (Initial focus state: `@radix-ui/react-roving-focus@1.1.19 dist/index.mjs:50`, Tablist tabindex: `@radix-ui/react-roving-focus@1.1.19 dist/index.mjs:92`, Trigger registration and tabindex: `@radix-ui/react-roving-focus@1.1.19 dist/index.mjs:139`, [Panel props](https://github.com/ReynkeDeVos/portfolio-next/blob/7a1bb0d/src/components/portfolio-page.tsx#L92).)

The inspected official [Tabs docs](https://www.radix-ui.com/primitives/docs/components/tabs) document controlled selection and keyboard behavior; the [SSR guide](https://www.radix-ui.com/primitives/docs/guides/server-side-rendering) documents server rendering and ID behavior. Neither supplies a fragment-selected, prehydration Tabs pattern. The Tabs docs currently display 1.1.18, so installed 1.1.21 source governs the details above. Root `suppressHydrationWarning` supplies no alternate Tabs value or ARIA/focus reconciliation; the page’s layout effect performs that handoff. ([Root rendering](https://github.com/ReynkeDeVos/portfolio-next/blob/7a1bb0d/src/routes/__root.tsx#L31), [Section handoff](https://github.com/ReynkeDeVos/portfolio-next/blob/7a1bb0d/src/components/portfolio-page.tsx#L22).)

## Implications for Section navigation

The Section owner must define one synchronization contract covering selection, URL, Locale destinations and traversal. Direct replacement is observed in these installed versions, so it must not be treated as a way to avoid router loading. Router-supported navigation makes replacement, blockers and scroll policy explicit; preserving search requires an explicit choice.

The owner must preserve history metadata when using native history methods, distinguish browser hashes from router hashes, and handle router hash updates without relying solely on `hashchange`. Replacing Sections intentionally makes Back traverse page/Locale entries rather than individual Section choices.

The owner must also preserve the server/client initial-render contract and keep visible content aligned with semantic selection through the hydration handoff. A reactive hash hook alone does not solve prerendering parity. A CSS-only Section mark does not establish an alternate accessible selected tab, and `forceMount` does not initialize keyboard behavior.

## Unresolved

Browser execution, scroll positions, rapid-click/Locale-navigation races and assistive-technology announcements were not tested. The conclusions are source-derived; exact render counts and hydration diagnostics remain unverified.

No complete prehydration fragment-selection recipe was found in the inspected Radix Tabs and SSR guides. This does not establish that no such pattern exists elsewhere. Live TanStack docs are unpinned; installed source versions govern this note.
